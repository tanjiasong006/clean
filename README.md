# Clean

使用 Rust、GPUI 和 GPUI Kit 构建的磁盘空间分析工具，支持 macOS 和 Windows。

当前已实现目录扫描与导航循环，并加入大文件分析和 macOS Finder 集成。架构和首版范围见 [AGENTS.md](AGENTS.md)。

## 当前功能

- 显式选择主目录、下载目录或其他目录，多个后台工作线程并行扫描。
- 增量显示已发现的文件路径数、目录数和已分配空间；扫描期间可以取消并保留已有结果。
- 按大小降序浏览目录和文件，显示已发现大小的占比；双击目录进入，通过面包屑或返回按钮导航。
- 每个目录保留选中条目和滚动位置，切换分析视图后恢复；支持复制完整路径、在系统文件管理器中定位选中项（macOS 为 Finder，Windows 为资源管理器）。
- 大文件视图汇总整个扫描范围内去重后的普通文件，按已分配空间降序显示，可选择全部文件、≥100 MiB、≥1 GiB 或 ≥10 GiB；支持跳转到所在目录并选中该文件。
- 单独显示所选卷的容量和当前用户可用空间；后台查询失败时明确提示，不影响目录扫描。
- 单独查看读取失败的路径与原因；未读完或含失败项的目录标记为不完整，不视为空目录。

偏好持久化、更多性能优化和 macOS 打包将在后续阶段加入。尚未实现删除或清理功能。

## 统计规则

只统计文件系统报告的**已分配空间**，不再汇总或展示文件逻辑长度。macOS 读取 `st_blocks × 512`，固定以 512 字节为单位换算，与 `statfs` 的文件系统块大小无关；Windows 读取文件系统在目录枚举或句柄查询中报告的分配量；以二进制单位显示（KiB、MiB、GiB）。普通文件和目录自身报告的分配量均计入，目录行还包含其子条目的贡献；因此目录自身有分配量时，子条目的占比之和可以小于 100%。符号链接和特殊文件不计入字节总数，不遍历符号链接。目录数量包含所选根目录。

硬链接在**每次扫描内按设备号与 inode 去重**，不是按路径或内容去重。同一文件的分配量归入本次扫描首次发现的路径及其祖先，其他路径保留在目录列表中，但标为“已去重”并显示计入的路径，不再增加目录或扫描总量。文件数仍为发现的普通文件路径数，另列去重路径数；大文件索引只收录首次发现的文件路径，包括分配量为零的稀疏文件。跨目录硬链接的归属取决于发现顺序，目录合计表示本次扫描分配到该目录的贡献，不是对该子目录单独执行扫描的结果；重新单独扫描该目录会重新去重并计量。去重表只为硬链接数大于 1 的普通文件保留身份与首个节点 ID，单链接文件不占用表项；不复制路径，内存随多链接文件数增长，扫描线程结束后释放。

稀疏镜像只计入系统报告的已分配块，而不是其声明的数百 GiB 或 TiB 的逻辑长度。排查单个文件时，可使用 `stat -f 'allocated_blocks_512=%b hard_links=%l' /path/to/file` 对照 `du -k /path/to/file`；对于稀疏但尚未写入数据的文件，已分配空间可以为零，这不表示文件内容长度为零。

**已分配空间不等于独占占用或删除后可释放空间。** APFS 克隆、快照和共享数据不按 inode 去重，仍可能重复报告共享块；macOS 扫描允许跨挂载点，不把总量限制在单个卷的容量以内；Windows 首版不跨卷。界面在总量超过所选卷容量时提示这些差异，不把总量截断，也不声称其与系统显示的磁盘已用总量一致。未纳入扫描范围的系统元数据等也不在扫描总量中。

读取失败或文件在读取元数据前消失，会保留其他结果并将扫描标记为不完整；根目录无法读取时显示失败。取消扫描也保留已发现的结果。扫描期间文件可能继续变化，大小取读取元数据时观察到的值，结果不是文件系统快照。已分配空间累加溢出时保留已发现条目，明确报告统计范围溢出，并将结果标记为不完整，不显示溢出目录的精确大小或占比。

macOS 扫描以打开的根目录句柄为锚点；子目录从父目录句柄按单个名称 `openat` 且禁止跟随链接的方式打开。目录条目通过 `getattrlistbulk` 批量读取名称、类型、设备号、inode 和已分配空间；卷不支持批量读取时回退为 `readdir` 加 `fstatat`。因此目录中的元数据是**列出该目录时**观察到的值，之后发生的文件增长不计入本次扫描。待扫描目录的设备号或 inode 变化时，记录问题并跳过替换内容。已打开的根目录或正在读取的目录被重命名后，仍读取原目录，不转入同名路径的新内容。结果中的路径是扫描时观察到的路径，之后可能不再有效。

Windows 扫描同样以打开的目录句柄为锚点：子目录按单个名称用 `NtCreateFile` 相对父句柄打开，条目通过 `FileIdExtdDirectoryInfo` 一次性读取名称、分配量、重解析点标签与 128 位文件 ID；文件系统不支持该信息类（FAT/exFAT、部分 SMB 服务器）时，从目录开头改用 `FileIdBothDirectoryInfo` 重读，该布局没有 128 位 ID，因此这个目录不参与硬链接去重，重解析点条目按名称单独探测标签。枚举缓冲区为 64 KiB，低于部分 SMB 服务器对该调用的上限，也远大于单条记录。只有 NTFS 和 ReFS 使用文件 ID 去重；FAT/exFAT 及网络卷返回的 ID 不可靠，这些卷会关闭去重。根目录先用只读属性权限打开并确认是真实目录，再以列目录权限按路径打开并复核身份，避免把普通文件误报为权限不足。每次扫描通过 `DuplicateHandle` 复制这个已打开的根句柄，因此根目录被重命名或路径被替换后仍读取原目录。该批量结构不提供链接数，因此每个具有有效文件 ID 的普通文件会按名称额外打开一次读取 `NumberOfLinks`；文件被独占锁定或探测失败时按 1 个链接处理，不标记扫描不完整，但该文件可能不会被识别为别名。符号链接与目录联接不遍历；其他目录重解析点记为特殊项；文件重解析点（例如云占位符）按普通文件计入其报告分配量，不读取内容，也不触发下载。Windows 首版不跨卷：挂载点本身是重解析点，会被跳过。NTFS 通常对目录报告 0 分配量，所以 Windows 上目录自身分配量一般不计入。名称按 WTF-8 保存，可精确还原含孤立 UTF-16 代理项的路径；界面显示可能使用替换字符，排序按 WTF-8 字节序，与资源管理器的本地化排序不同。

目录列表的占比条以当前目录本次扫描计入的**已分配空间**为分母；大文件列表以整个扫描范围的已分配空间总量为分母。两者均不表示扫描进度。扫描总数不代表独占占用、磁盘容量或可释放空间。

卷容量与可用空间在开始扫描时单独查询：macOS 使用 `statfs`（64 位块计数，按文件系统块大小换算），Windows 先用 `GetVolumePathNameW` 找到包含所选路径的卷挂载点，再用 `GetDiskFreeSpaceExW` 查询，因此挂载到文件夹的卷报告自身容量，而不是宿主盘符的容量；可用空间均取当前用户可用字节数。这不是可清理空间估算，也不计算 APFS 共享数据或可清除空间。文件管理器定位不会解析符号链接：macOS 选中的是链接本身，Windows 通过资源管理器的 `/select` 参数定位；目标消失或系统命令失败时显示错误。

## 开发环境

- macOS 15 或更高版本，或 Windows 10/11。
- Rust stable，包含 Cargo、rustfmt 和 Clippy；工具链要求见 `rust-toolchain.toml`。
- macOS 需要 Xcode 或 Xcode Command Line Tools，使用 `xcode-select -p` 检查开发工具路径；Windows 需要 MSVC 生成工具（Visual Studio Build Tools 中的“使用 C++ 的桌面开发”）。
- Windows 的 release 构建需要 Windows SDK 中的 `fxc.exe` 编译 GPUI 的 HLSL 着色器；安装上述 MSVC 生成工具时通常已包含。debug 构建跳过着色器编译，因此在 macOS 上只能交叉构建 Windows debug 版本。

GPUI Kit 使用统一依赖入口，包含匹配的 GPUI、组件和默认图标资源。参考[官方安装说明](https://gpui-kit.com/docs/installation/)及[入门文档](https://gpui-kit.com/docs/getting-started/)。

## 运行与检查

仓库已包含 `Cargo.lock`，使用锁定的依赖运行和检查：

```sh
cargo run --locked
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo build --locked
```

Windows 上使用相同的命令。另可在 macOS 上交叉检查 Windows 目标：

```sh
cargo check --locked --all-targets --target x86_64-pc-windows-msvc
```

也可用 [cargo-xwin](https://github.com/rust-cross/cargo-xwin) 交叉链接测试程序，并在 Wine 中执行：

```sh
cargo xwin test --locked --no-run --target x86_64-pc-windows-msvc
wine target/x86_64-pc-windows-msvc/debug/deps/clean-<hash>.exe
```

Wine 未实现 `FileIdExtdDirectoryInfo`，目录枚举会走回退布局，依赖文件身份的硬链接去重与替换检测用例会自动跳过；Wine 的 DXGI/DirectX 也无法初始化，不能用于界面验证。因此 Wine 只能补充扫描后端的回归检查，最终以 Windows 实机或 Windows CI 为准。

交叉构建的 debug 版在 Windows 上启动还需要着色器源文件：debug 版在运行时用 `D3DCompileFromFile` 编译 HLSL，而 gpui-pre-windows 把**构建机**上的 `CARGO_MANIFEST_DIR` 写进了可执行文件，目标机上该路径不存在时以 `os error 3`（找不到路径）失败。要在目标机运行这类 debug 构建，需按该路径放置 `shaders.hlsl`、`color_text_raster.hlsl` 和 `alpha_correction.hlsl`；`target/windows-debug-shaders/gpui-pre-windows-<版本>/src/` 保留了一份按相同布局整理的文件。release 构建在编译期把着色器字节码嵌入二进制，不依赖这些文件。

首次构建会下载并编译 GPUI 依赖，耗时较长。扫描器的临时目录测试覆盖目录聚合、排序、符号链接、硬链接、取消、读取失败、扫描期间文件变化和后台批量更新。权限失败通过文件系统边界注入，以便测试在不同权限的环境中均可重复执行。额外覆盖目录及祖先目录被替换为符号链接、目录身份变化、打开目录后的路径替换、开始前/迭代期间取消、接收端断开、通道背压、160 层目录、稀疏大文件与特殊名称。批量聚合以逐事件参考算法校验不同批次边界，并测试统计溢出。额外测试覆盖大文件筛选边界、增量索引、视图切换与目录导航状态、卷容量换算，以及 Finder 命令的字面路径参数（不启动 Finder）。Windows 条目解析、两种目录记录布局和重解析点分类放在纯 Rust 模块中，可在任意主机运行测试；真实文件系统用例在 Windows CI 上执行，创建符号链接需要开发者模式或相应权限，权限不足时跳过相关用例。

## 安装包

本地构建安装包（先执行 `cargo build --locked --release`）：

```sh
packaging/macos/package.sh 0.1.0 target/release/clean dist
```

生成 `dist/Clean-0.1.0-macos-<架构>.dmg`，内含 `Clean.app` 和指向 `/Applications` 的快捷方式。应用使用 ad-hoc 签名、未公证，首次打开需右键选择“打开”。

```powershell
powershell -File packaging\windows\package.ps1 -Version 0.1.0
```

生成 `dist\Clean-0.1.0-windows-x86_64-setup.exe`，需要 NSIS 的 `makensis.exe`。安装包按当前用户安装到 `%LOCALAPPDATA%\Programs\Clean`，创建开始菜单快捷方式并注册卸载项，不需要管理员权限。安装包和 exe 未做代码签名，Windows SmartScreen 可能提示。Windows release 通过 `.cargo/config.toml` 使用静态 CRT，不依赖 VC++ 运行库。

图标源文件为 `packaging/icons/clean.svg`，生成的 `clean.icns` 用于 macOS 应用包，`clean.ico` 由 `build.rs` 通过 `embed-resource` 嵌入 Windows exe（资源 ID 为 1，GPUI 据此设置窗口图标），同时随安装包安装供快捷方式使用。在 macOS 上交叉构建 Windows 版本时，需把 Homebrew LLVM 的 `llvm-rc` 加入 `PATH` 才会嵌入图标；找不到时跳过嵌入，构建仍然成功。

## 项目结构

```text
src/main.rs       应用入口和窗口初始化
src/ui/           GPUI Kit 界面
src/scanner/      后台遍历、批量事件和取消
src/analysis/     大小排序、大文件增量索引和格式化
src/platform/     平台目录入口、卷查询、文件管理器集成和平台扫描后端
src/models/       扫描状态、条目和目录聚合
```

扫描和分析模块不依赖 GPUI。

- 扫描线程按可用并行度启动最多 16 个工作线程，共享一个待扫描队列；每批最多 128 条事件，通道容量随工作线程数增长，通道满时施加背压，不无限缓存扫描事件。同一目录的条目事件连续发送，结果模型据此把子节点存为连续区间。
- 工作线程持有正在读取的目录句柄；待扫描的子目录保存父目录句柄、短文件名与身份，不复制完整路径。队列采用后进先出，使保留的父目录句柄接近当前遍历深度，实测峰值约 51 个打开目录；文件描述符软上限在扫描前提升到系统的硬上限（最多 4096）。遍历不使用递归调用栈。
- 聚合按批次从子节点向父节点合并，每个受影响的祖先在一批中只更新一次。
- 当前目录与大文件使用有序索引；只更新新增条目及大小改变的目录，避免对全部结果反复排序。索引只保存 4 字节节点 ID，路径由扫描结果的紧凑名称区按需重建，不复制路径内容。大文件索引只收录分配量不低于 100 MiB 的文件，更低的筛选阈值按需回退为遍历全部文件。
- 界面每约 16ms 消费更新，每轮最多 32 批，在批次之间检查约 4ms 的处理时间预算；可见 ID 列表最多每 100ms 重建一次，结束时立即刷新。时间预算不包括操作系统阻塞，也不是整帧耗时的硬上限。
- 结果列表仍为虚拟化渲染。扫描结果和索引目前保存在内存中，尚未做磁盘索引：每个条目固定 6 字节（24 位名称字典 ID 与 24 位 kind/负载），名称按内容去重后存入共享字典（每个唯一名称 1 字节长度，另每 32 个唯一名称一个 4 字节块偏移），目录记录为 24 字节（读取错误数与大小溢出标志存放在稀疏旁表），硬链接别名表按节点顺序存为 8 字节的（别名 ID、首个 ID）对。扫描期间另有名称哈希表，进入终态后释放。一次扫描最多容纳 16,777,216 个唯一名称与 4,194,304 个目录；分配量约 2 GiB 及以上的文件把精确字节数放入旁表。3,000,000 个合成文件的请求堆内存：名称全部唯一（字典最差情况）时扫描完成后为 72.75 MiB、峰值为 91.24 MiB，约四成名称唯一（接近实测主目录分布）时分别为 53.84 MiB 和 63.99 MiB；该数字来自合成基准，不是 RSS，也不包含 GUI 开销。Windows 的扫描吞吐、硬链接探测开销和内存尚未记录，不能直接套用上述 macOS 数字。

## 核心性能验证

历史实测环境、测试结果、基准数据和验证限制见 [2026-10-24 扫描验证记录](docs/testing/2026-10-24-scan-validation.md)。该记录保留了切换前的逻辑大小口径，不代表当前已分配空间口径的测试结果。

合成基准直接编译扫描结果聚合与分析模块，不启动 GUI，也不需要重新编译 GPUI：

```sh
perf_dir=$(mktemp -d)
rustc --edition=2024 -O scripts/core_perf.rs -o "$perf_dir/core-perf"
"$perf_dir/core-perf"
```

基准每次处理十万条目，分别测量平铺目录的聚合与索引更新，以及 96 层祖先的批量聚合。会校验条目数、总大小和排序，不设易受机器负载影响的时间阈值。这是内存合成基准，**不是磁盘扫描吞吐或 GUI 帧率**。

`--memory <条目数>` 模式通过全局分配器统计请求的堆内存（不是 RSS）：模拟一次扫描在扫描中与完成后的常驻字节，并同步维护两个索引。默认一百万条，分别按“全部名称唯一”和“约四成名称唯一”两种名称分布执行一次：

```sh
"$perf_dir/core-perf" --memory 3000000
```

真实文件系统的手动压力测试会创建并自动清理两万个临时稀疏文件，验证后台扫描、有界通道、批量聚合和两个排序索引：

```sh
cargo test --locked large_directory_worker_pipeline -- --ignored --nocapture
```

测试输出不包含准备/清理文件的时间，也不包含 GUI 的轮询间隔；新建文件通常处于热缓存，不能直接外推到冷盘、网络卷或用户主目录。

真实目录的扫描吞吐可用默认忽略的基准单独测量（release 构建，不启动 GUI）。默认扫描主目录并忽略事件，设置 `CLEAN_BENCH_APPLY=1` 时额外执行一次带聚合与索引的完整扫描：

```sh
CLEAN_BENCH_ROOT="$HOME" CLEAN_BENCH_ROUNDS=3 \
  cargo test --release --locked benchmark_real_tree -- --ignored --nocapture
```

| `~/project` | 904k | 28.63 s | 3.35 s | 约 8.5 倍 |
| `~/Library` | 912,008 | 48.82 s（18.7k 条/s） | 5.5–10.3 s | 约 4.8–8.9 倍 |

以上是单机单次负载下的观测值，不是耗时门槛；冷缓存、外置磁盘和网络卷的结果会不同。剩余耗时主要来自每个目录约 40 µs 的打开与批量读取，以及单卷上约 3 倍的并行扩展上限（主目录扫描期间 `user` 约 2.4 s、`sys` 约 44 s）；继续提高并发反而下降，例如 `~/Library` 使用 16 个工作线程时约 17 s。

## 版本管理

主分支使用 `main`，提交 `Cargo.lock` 以固定应用依赖。构建产物、日志及本地环境配置由 `.gitignore` 排除；`.gitattributes` 统一文本换行。

macOS 与 Windows CI 对主分支推送和拉取请求执行格式、Clippy、测试及构建检查。推送任意 tag 时，两个任务在检查通过后还会各自构建 release 并上传安装包 artifact：macOS 为 `Clean-<版本>-macos-<架构>.dmg`（ad-hoc 签名，未公证），Windows 为 `Clean-<版本>-windows-x86_64-setup.exe`。
