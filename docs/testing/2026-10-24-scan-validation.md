| malloc 活跃量 | 10.9 MiB | 107.0 MiB | 96.1 MiB |
| 扫描结果 arena 合计 | — | 93.8 MiB | 93.8 MiB |

扫描完成后 5 秒与 30 秒的采样基本不变，没有自动回落的趋势。`phys_footprint` 在不同轮次间波动可达约 20 MiB，与压缩页有关；比较时取 `/usr/bin/footprint` 的稳定值或同一轮次内的差值。

扫描结果明细（`shrink_to_fit` 之后）：

| 部分 | 大小 |
| --- | ---: |
| 名称区 | 57.0 MiB |
| 节点 | 21.0 MiB |
| 目录记录 | 9.9 MiB |
| 硬链接表 | 3.7 MiB |
| 目录/大文件索引 | 1.1 MiB |
| 目录名称前缀 | 1.0 MiB |

未扫描与扫描完成后的 `footprint` 分类对比：

| --- | ---: | ---: |
| `MALLOC_SMALL` | 19 MB | 84 MB |
| `MALLOC_LARGE` | 未单列 | 61 MB |
| `IOSurface` | 25 MB | 25 MB |
| 进程 `phys_footprint` | 58 MB | 185 MB |

### 结论

- Activity Monitor 中约 180M 的读数与 `phys_footprint` 口径一致，约等于 58M 的无扫描基线加 94M 的真实扫描数据，再加约 30M 的小对象分配器碎片和高水位。
- 未扫描基线中的 `IOSurface`（约 25 MB）属于窗口和 GPU 相关开销，不随扫描结果增长。
- 扫描结束后调用 `malloc_zone_pressure_relief` 实测返回 0 B，不存在可归还的整体空闲页；多出的约 30 MB 是小对象区中无法整页归还的碎片。
- 目录表此前按倍增扩容，真实规模下预留 16.0 MiB 而只需 9.9 MiB；进入终态时 `shrink_to_fit` 收回约 6.1 MiB，扫描结果合计从 100.0 MiB 降到 93.8 MiB。
- 名称区仍是最大项（57.0 MiB）。继续降低需要名称压缩或字典编码，属于新的设计改动；当前不做。
- 以真实 271 万条目计，扫描结果的活跃内存约为每节点 35 B，与紧凑存储布局的估算一致。

### 限制

- 只测量了一个主目录、热缓存、单机单次负载下的结果，未覆盖冷盘、网络卷和外置磁盘。
- 未使用已授权的 `.app` 运行，条目数和读取问题数不等同于用户实际使用场景；内存随条目数线性增长，可用本次数据按比例估算，但不能直接当作其他目录的绝对值。
- `phys_footprint` 包含压缩页和窗口相关映射，受系统内存压力影响；绝对读数存在约 10 MiB 级波动，本记录以稳定值和差值为主。
- 临时探针已移除，当前提交不提供运行时内存采样开关；后续如需重复测量，应重新加入探针或改用 `/usr/bin/footprint -p <pid>`。

## 后续回归：并行批量扫描提速

### 验证范围与时间

2026-10-24 本轮复测，沿用上述本机环境与锁定依赖，使用 release 构建并只统计扫描事件，不启动 GUI。范围是把 macOS 目录遍历从“每个条目一次 `fstatat`、按完整路径逐层打开子目录”改为：

- 每个目录一次 `openat`，从父目录句柄按单个名称打开，仍禁止跟随链接；
- 用 `getattrlistbulk` 一次读取多个条目的名称、类型、设备号、inode、硬链接数与已分配空间，不支持批量读取时回退为 `readdir` 加 `fstatat`；
- 按可用并行度启动最多 16 个工作线程，共享待扫描队列，每批最多 128 条事件；
- 硬链接去重在同一把发送锁内按首次发送顺序完成，保证同一次扫描内的归属与旧实现一致。

对照实现来自同一提交 `8abf93b` 的临时 git worktree，加入相同的计数回调后单独构建 release 二进制，测量结束已移除。两侧使用同一份 `Cargo.lock`、相同目录和热缓存状态；下表比较的是扫描本身，不包含聚合、索引或 GUI。

### 方法与复现

当前实现的基准测试默认忽略，默认扫描 `$HOME`；可用环境变量指定目录、轮次和是否附加一次带聚合的完整扫描：

```sh
CLEAN_BENCH_ROOT="$HOME" CLEAN_BENCH_ROUNDS=3 \
  cargo test --release --locked benchmark_real_tree -- --ignored --nocapture
```

设置 `CLEAN_BENCH_APPLY=1` 时，每轮额外执行一次带聚合与索引的完整扫描，并打印其耗时；这会扫描两遍，不能与纯扫描耗时直接相加或比较。

### 结果

| 目录 | 条目数 | 旧实现 | 当前实现 | 提速 |
| --- | ---: | ---: | ---: | ---: |
| 主目录 | 2,712,176 | 101.82 s（26.6k 条/s） | 13.24 / 13.35 / 14.24 s（190k–205k 条/s） | 约 7.2–7.7 倍 |
| `~/project` | 904k | 28.63 s（31.6k 条/s） | 3.35 s（270k 条/s） | 约 8.5 倍 |
| `~/Library` | 912,008 | 48.82 s（18.7k 条/s） | 5.5–10.3 s | 约 4.8–8.9 倍 |

主目录三轮均报告约 2,712,176 个条目与 146–148 个读取问题；终端进程未获得完整磁盘访问权限，问题数高于已授权应用。旧实现的主目录仅为单轮结果；首次运行时曾超过十分钟，未能复现，表中只保留可重复测量的 101.82 s。

主目录扫描期间进程 CPU 时间约为 `user` 2.4 s、`sys` 44 s，绝大部分时间在内核中等待和读取元数据，而不是本项目的 Rust 代码。按约 323,500 个目录、每个目录一次打开加一次批量读取估算，剩余约 13 s 已接近该卷在本机的元数据访问下限；单卷上的并行扩展约 3 倍，继续增加线程反而下降：

| 工作线程 | `~/Library` 热缓存耗时 |
| ---: | ---: |
| 4 | 约 7.5 s |
| 8 | 约 5.6 s |
| 16 | 约 17.3 s |

扫描期间同时打开的目录句柄峰值为 51（采样 LIFO 遍历下的读数），远低于提升后的 4096 软上限。因此本轮结果是真实主目录约 7–8 倍，而不是 100 倍；100 倍需要减少或绕过每个目录都必须付出的内核元数据访问，当前接口没有可用手段。

### 正确性语义变化与测试调整

| 行为 | 当前语义 |
| --- | --- |
| 元数据观察时点 | 目录被列出时记录；之后文件增长或缩小不影响本次扫描结果 |
| 单条目读取失败 | 保留该条目的名称与路径，记录问题并将扫描标记为不完整；不再只记录目录级失败 |
| 待扫描目录被替换 | 打开后比较设备号与 inode，不一致时跳过替换内容 |
| 祖先目录被替换为重命名或链接 | 已持有父目录句柄，继续读取原目录；不转入同名路径的新内容 |
| 并行发送顺序 | 同一目录的事件仍作为连续区间发送；目录 ID 在发送时分配，父目录先于子目录 |
| 硬链接归属 | 仍为本次扫描首次发送的路径；跨工作线程的竞争由发送锁消除 |
| 不支持批量读取的卷 | 回退为 `readdir` 加 `fstatat`，仍不跟随链接 |

相应测试已调整：文件在列出后增长时断言列出时的分配量；文件在元数据读取前消失时由条目错误携带名称；祖先被替换为重命名目录时断言完整读取原目录；新增按工作线程数运行的并行测试与上述真实目录基准。`CLEAN_SCAN_WORKERS` 仅用于测试，可覆盖工作线程数。
