## 合成性能基准

### 方法与复现

每轮生成十万条普通文件事件，按最多 1024 条事件更新：

1. 平铺目录：计入路径生成、目录聚合、大文件索引、目录排序索引更新及可见 ID 列表生成。
2. 深层聚合：父节点关系形成 96 层祖先链，仅测量事件生成与聚合，不创建真实的深层文件系统目录。

准备祖先节点与计时后的正确性断言不计入耗时。当前实现以独立程序优化编译，不启动 GUI：

```sh
perf_dir=$(mktemp -d)
rustc --edition=2024 -D warnings -O scripts/core_perf.rs -o "$perf_dir/core-perf"
"$perf_dir/core-perf"
```

主目录扫描截图显示逻辑总量约 818.3 GiB，高于所选卷容量。排查发现本机 OrbStack 的 `data.img.raw` 是一个主要差异来源；仅读取文件元数据，没有读取镜像内容或修改镜像：

| 指标 | 观测值 |

| 文件系统报告的分配量 `st_blocks × 512` | 8,676,048,896 B，约 8.080 GiB |

单个文件的两种口径已有约 452.352 GiB 差异，说明逻辑总量超过卷容量不必然是重复计数。此次没有独立重新聚合截图中的全部文件，不能据此排除所有其他扫描问题，也不能从 818.3 GiB 中减去该差值就得到整个主目录的实际占用。截图中的扫描状态仍为不完整。

`st_blocks × 512` 与 `du` 的一致性不代表已获得 APFS 独占或可回收字节数；共享数据和硬链接等仍需单独设计统计口径。

### 三百万条目内存结果

`scripts/core_perf.rs` 的 `--memory` 模式用全局分配器统计**请求的堆内存**，不是 RSS，也不启动 GUI：

```sh
rustc --edition=2024 -O scripts/core_perf.rs -o /tmp/clean-core-perf
/tmp/clean-core-perf --memory 3000000
```

```text
3000000 files; requested heap only, not RSS
scanning with dedup + two indexes: live=76.46 MiB, peak=76.46 MiB
finished with two indexes: live=57.45 MiB, peak=77.45 MiB
```

合成输入包含长尾大小分布（约千分之一为 MiB 级文件）、每万条一个多链接文件，并在扫描中与结束后各维护一次目录索引和大文件索引。结果满足三百万条目低于 80 MiB 的请求堆内存目标。峰值出现在扫描期间：此时名称、节点、目录记录和索引同时驻留；结束后去重表释放，目录索引恢复为已排序状态，常驻值下降。

### 存储布局

| 数据 | 每条开销 | 说明 |
| --- | ---: | --- |
| 节点记录 | 8 B | 名称偏移 + 打包的种类与载荷；文件载荷为块数，小文件不需额外记录 |
| 名称 | 实际字节数 | 分块名称区，无终止符；名称长度由下一节点偏移推导 |
| 目录记录 | ≤ 32 B | 子节点区间、字节数、错误数、前缀长度等 |
| 索引条目 | 4 B | 目录与大文件索引只保存节点 ID，路径按需重建 |
| 待扫描目录 | 常数 + 文件名 | 只保存父目录序号、文件名与身份，不复制完整路径 |

同一目录的子条目名称共享公共前缀，前缀在每个目录关闭时只存一份；目录字节数只写入目录记录一次，不再为每个祖先保留副本。界面直接从索引读取可见条目，不再维护重复的可见 ID 列表。
